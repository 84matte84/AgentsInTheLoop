## CWE-502: Deserialization of Untrusted Data

We eliminated native Java serialization from our platform and replaced it with schema-validated, allowlisted deserialization across all service boundaries.

**The threat model:** Untrusted data entering a deserialization routine can instantiate arbitrary objects, trigger gadget chains, and achieve remote code execution. The classic ObjectInputStream nightmare.

**Our mitigations:**

- Banned `ObjectInputStream` via static analysis rules (Semgrep + CI gate). Any PR introducing native Java deserialization is automatically rejected.
- All inter-service communication uses Protocol Buffers with strict `.proto` schemas. No polymorphic types, no `Any` fields in external-facing APIs.
- For legacy systems that still require JSON deserialization, we use Jackson with `DefaultTyping` disabled and explicit `@JsonTypeInfo` on a per-class allowlist.
- Message queues (Kafka) enforce schema registry validation — messages that don't match the registered Avro schema are dead-lettered.
- Runtime protection: Java agent that hooks `ObjectInputStream.resolveClass()` with a deny-by-default policy. Only 12 classes are permitted, all value objects.

```java
// Deserialization filter (JEP 290) - production config
jdk.serialFilter = \
  maxdepth=5;\
  maxrefs=500;\
  maxbytes=500000;\
  !org.apache.commons.**;\
  !org.springframework.**;\
  com.ourplatform.dto.**
```

**Results:** 18 months in production, zero deserialization-related findings in pentests. CVE-2024-21733 (Spring framework deserialization) had zero impact on us because we never pass untrusted data through Spring's deserializer.

<AIJudgment persona="The Insider Threat Analyst">

## Assessment: Your Trust Boundary Is a Fiction

You hardened the front door and left the service mesh running on mutual trust and good intentions.

**The allowlist is a point-in-time artifact.** Your 12 permitted classes today were chosen by someone who understood the risk. In 6 months, a team ships a new DTO, adds it to the allowlist via a routine PR, and nobody notices it contains a nested collection with a custom comparator. Your allowlist review process has the same failure mode as every other security-critical code review: it works until the volume of changes makes careful review impractical.

**Protocol Buffers don't save you from logic bugs.** You eliminated type confusion but replaced it with something worse: confidence. Your teams believe inter-service messages are "safe" because they're schema-validated. But schema validation checks structure, not semantics. A malicious internal actor (or compromised service) can send a perfectly schema-valid message with `user_id: "admin"` or `amount: -999999` and your deserialization layer will happily reconstruct it.

**The real attack surface you're ignoring:**

1. **Build pipeline injection** — Your Semgrep rules check source code. They don't check transitive dependencies pulled at build time. A compromised internal library (think dependency confusion or a malicious maintainer on one of your 300+ transitive deps) can introduce deserialization gadgets that your static analysis never sees because they aren't in *your* source.
2. **Schema registry as single point of trust** — If I compromise your Confluent Schema Registry (or its backing store), I can register a schema that adds fields your consumers will silently parse. Schema evolution rules allow adding optional fields — I just added a field that your downstream service deserializes into a type that triggers initialization logic.
3. **The Java agent has a kill switch** — Your runtime filter hooks `resolveClass()`. In JVM ergonomics, `-XX:-EnableJVMCI` or a well-crafted agent load (via `com.sun.tools.attach`) from a compromised co-resident container can disable or replace your agent. You're one container escape away from naked deserialization.

**The cultural problem:** Your team says "we eliminated native Java serialization." But your JVM still has `ObjectInputStream` in `rt.jar`. Your framework dependencies (Spring, Hibernate, Hazelcast, if you use it) still contain gadget chains. You've made exploitation *harder* — you haven't made it *impossible*. The difference matters when your threat model includes a determined insider.

```
ATTACK CHAIN: Compromised internal library
  → transitive dep with gadget class
  → allowlist PR to add "harmless" DTO
  → DTO contains List<Comparable>
  → attacker-controlled comparator
  → RCE from inside your trust boundary
```

**Your pentests found nothing because pentesters test from outside.** Your real risk is lateral movement from an already-compromised internal service — and for that attacker, your mitigations are speed bumps, not walls.

</AIJudgment>

## The Analysis

The Insider Threat Analyst correctly identifies the class of risk we accepted when we scoped our threat model to external attackers. But it conflates "not impossible" with "not effective."

**Where the AI is right:**

- The allowlist review process is genuinely the weakest link. We've had two cases where a DTO was added without security review. Neither was exploitable, but the process gap is real.
- Schema validation checking structure but not semantics is a fair point. We do have separate input validation layers, but they're not uniformly applied across all consumers.
- The supply chain attack via transitive dependencies is our actual nightmare scenario. We use Dependabot and have a lock file, but a targeted dependency confusion attack would likely succeed for a window before detection.

**Where the AI overstates the risk:**

- The Java agent "kill switch" argument assumes container escape, which is a separate and much harder vulnerability class. If an attacker has container escape, we have bigger problems than deserialization.
- Schema registry compromise requires privileged access to a hardened internal service. It's a valid attack tree node but not a realistic first-step vector.
- The "pentesters test from outside" claim is false for us — we run annual red team exercises with assumed-breach scenarios and internal starting positions.

**What we're changing:**

After this analysis, we're adding automated review of allowlist changes (any modification to the deserialization filter config requires Security team approval, enforced via CODEOWNERS). We're also evaluating runtime SCA to detect gadget-capable classes in loaded dependencies, not just source code.

> **Key takeaway:** CWE-502 mitigations that focus solely on the deserialization mechanism miss the broader trust boundary problem. The AI correctly identified that our defenses assume a perimeter that doesn't exist for insider threats — even if the specific exploitation scenarios require chaining multiple unlikely conditions.
